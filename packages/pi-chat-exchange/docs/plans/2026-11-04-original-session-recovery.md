## Design

1. Reuse existing recover-stale-ownership.mjs with an operator-owned Pi-target binding config and exact inspected owner tuple. Reuse existing reconcile-session-process-mutex.mjs offline, with all relevant openers stopped and inhibited. Do not change either tool or frozen Authority semantics. Keep receipts and original history.
2. Add explicit TUI-only `/ce-tunnel recover` for the current loaded v2 registration's original native Session and Endpoint. Never select a sender/Endpoint through command arguments. Display exact old mapping and Store, explain new durable Session creation, and require confirmation. No transport operation. Refuse other Endpoint failures, missing stable entry IDs or full history, changed policy/environment/session/branch, active local generation, any process failure cache for this native session, and a failed global runtime key. The latter requires process exit, not cache reset. A new process after offline reconciliation is the supported recovery boundary.
3. Use stable Pi custom-entry IDs to identify exact pre-existing lifecycle-blocked entries. Keep append-only recovery-attempt and recovery-resolved entries scoped to Store, native session, Endpoint, old mapping and those failure IDs. Attempt additionally has a random attempt ID and captured selected policy identity. Missing, malformed, mismatched or incomplete evidence denies. Validate the unknown entry-data boundary once in a small extension-local helper if needed.
4. Persist attempt before any new runtime/Host writes. Acquire the ordinary local mutex and current v2 policy facade, then call the ordinary Host `beginSession(endpointId, { requireUnowned: true })`. No override of runtime failed state, mutex acquisition, policy checks, or Owner checks. Before mutation, require unchanged branch/failure snapshot, context, environment and full captured policy. Recovery is valid after explicit offline cleanup; any remaining Owner, expired or active, refuses through the normal Host path.
5. Verify returned Participant and Exchange match the old mapping, durable Session differs, and Host reports ACTIVE exact new mapping. Append mapping and resolved evidence before publishing currentEndpoint/inbox generation or scheduling heartbeat/advisory. Recovery evidence contains identifiers only and never credentials. It is diagnostic, not authority. Do not fabricate ce-messaging-released.
6. On any failure after attempt, retain unresolved attempt/failure evidence, close/drain/drop the runtime and capabilities, and fail closed. Unknown results never automatically retry or auto-resume. Incomplete attempts are denied across full append history. Explicit recovery of a later independently inspected unknown attempt is out of this first narrow path; it stays a manual maintenance escalation. Do not pretend a pre-write refusal is uncertain ownership, but retain its attempt conservatively.
7. Centralize unresolved diagnostic interpretation for startup and activation. Exact successful resolution can discharge only its enumerated preceding failures in the same scope. Later failures and other Endpoints still deny. Only branch-visible resolved+new mapping may permit branch adoption; full-history records are additional deny-only evidence, including unfinished attempts and success hidden by branch rollback. Missing complete-history support retains old fail-closed behavior. Ordinary startup/reload/resume still validates/resumes latest branch mapping through Host. Bare new mapping cannot clear a failure.
8. Current Session stays Unknown while blocked or incomplete and becomes Attached only through existing realtime policy+ACTIVE+mapping checks. Report actionable fixed recovery/restart hints without payloads.

## Review amendments

- Persistence: recovery requires an existing on-disk native session file (ephemeral/unflushed sessions refuse). After each attempt/mapping/resolved append, locate the exact stable entry ID in the current branch and verify the same entry is actually present at the file tail through an O_NOFOLLOW regular-file descriptor with stable path/inode/UID identity. Sync that descriptor before any subsequent Host write or successful publication. The extension appends only through Pi; it never edits history directly. Bound the tail read; missing/mismatched entries refuse. Existing file mode 0644 is supported if other users cannot write it; identifiers only are persisted. This supports abrupt process-exit recovery and uses OS fsync for evidence, without claiming hardware/power-loss guarantees. Add an actual abrupt child-exit/restart test with persistent Pi-style history and isolated Store.
- Narrow scope: recovery requires at least one branch-visible persisted ce-lifecycle-blocked marker with a stable ID. Expired mapping without such a marker is explicitly unsupported by this first path: startup may latch the runtime, so report manual escalation and do not promise a fresh-process retry will fix it. Characterize/test both cases. The authorized production original session has the required marker.
- Concurrency: recovery shares activationTask/activationCapture coordination, busy checks, abort on session shutdown/replacement, and shutdown waiting. Revalidate exact branch and full-history snapshots immediately before attempt, and revalidate expected history including only that exact newly appended attempt before mutex/Host writes. Test simultaneous recovery/activation and replacement during confirmation.
- Commit visibility: the exact complete resolved entry is the journal commit point. The Host mapping/ACTIVE check and verified mapping persistence occur BEFORE appending it. If resolved append/verification/fsync throws after writing a complete visible entry, the current process closes admission, drops capabilities and stays latched; it does not announce success. On a fresh process, a complete branch-visible commit may be interpreted, but it grants nothing: startup must validate the exact recorded mapping through ordinary Host resume and current policy/mutex. Any later persisted failure still denies. An absent/partial/mismatched commit is an unfinished attempt and always denies. This deliberately allows fresh-start revalidation of a visible committed record when its writer did not observe confirmation; a local fsync error is not evidence that the already-verified CE Owner was never acquired. No automatic Host begin/takeover/retry is allowed. Test write-visible-then-throw, tail-check failure and fsync failure, with/without successful later failure-marker persistence, abrupt exit, and fresh startup. This narrows the earlier generic unknown-outcome wording: incomplete CE mapping/commit evidence denies, complete visible commit supports only ordinary authority revalidation.
- Review remediation: a later ordinary mapping may follow a recovery commit only through an exact intervening ce-messaging-released proof for its predecessor and this native session. Keep the recovery commit/mapping branch visibility requirements and ordinary Host resume authority checks; unrelated mappings, missing/wrong/out-of-order release proofs, hidden commits and later failures still deny. Cover real recovery → deactivate → activate → send → reload/resume, including the live-v2 policy reader used by deactivation.
