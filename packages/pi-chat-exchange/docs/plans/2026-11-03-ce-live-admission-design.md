# Live admission for one-command Connect — bounded contract design

Handoff: HANDOFF-CE-SESSION-ONBOARDING-01. Design revision **D3 (D2 plus discovery privacy and client-selection boundary remediation)**. Status: **READY_FOR_IMPLEMENTATION_AUTHORIZATION** following bounded D3 architecture and security PASS reviews and parent synthesis. This document does **not** authorize implementation, installation, migration, production operation or handoff closure. D1 review identified permission generations, pre-join routing, crash reconciliation and terminal port state. D2 security review identified undisclosed membership presence and non-enforceable user-selection requirements; D2 validation returned bounded PASS only for its original validation scope. D3 resolved those design findings; the implementation and real-peer evidence below remains required.

## 1. Scope, evidence and decisions requiring authorization

Source baseline is private main `64f6f1b4819d1316b293a948d63f690f63965d4f`. The design branch starts at evidence commit `15be180aebfcaa0bcd1c3304d9512ec24ebfe639`; the only preceding delta is the reviewed architecture-gate document. Existing production installation and Tunnel remain unchanged. Prior Daily Integration CLOSED remains valid for its original pi/main test; new-Endpoint messaging remains unverified.

The prior gate established three independent barriers: STOPPED-only publication/activation (`background-manager.ts:1734`, `multi-session-policy.ts:220`, extension activation); launch/current deny-only recipient intersection (`multi-session-admission.ts:16`, `multi-session-policy.ts:171`); Host-lifetime recipient capture (`endpoint-host.ts:451,500`). Previous characterization runs were 24 policy/onboarding tests plus two real stdio-child tests. They prove old behavior, not this design. No implementation experiment, actual live join or new cloud test has been performed for this design. Existing Pi `/ce-tunnel sessions` lists configured active registration labels only (`multi-session-commands.ts:44–54`), without Owner/loaded/adoption facts; the current MCP tools have no Endpoint discovery API. Existing exact recipient lookup and private Participant/Exchange/Owner rows already route by stable identity. This supplement reuses those facts and adds a bounded read-only projection rather than a second Endpoint Registry, broker or completion path.

This proposal explicitly requests internal architecture amendments: live-mode registration publication during transport execution; same-Host runtime recipient admission; stable launch/live-policy separation; per-permission loaded generation validation; release-only normal Disconnect; and an opt-in Endpoint discovery/authorized advisory observation interface. Each is a proposed change for separate implementation authorization. Frozen Protocol entities, Store SQL/schema/migrations, capability scope/issuance rules, recipient-only message visibility, Ownership/fencing/lease semantics, receipt formats, uncertain delivery, Hooks execution and Wayforge business Completion Authority remain unchanged. A private read-only aggregate may compose existing SELECTs/parsers without changing SQL definitions, tables or public storage exports. If an actual frozen API is found to prohibit these internal extensions, report the exact contract and return BLOCKED; do not weaken it silently.

Goal: one `/ce-tunnel connect`, with necessary native TUI consent, registers/binds its own Endpoint and reuses or starts transport. Connect success reports separate binding, policy-adoption and transport facts. Already authorized Sessions need no repeated messaging consent. New registration/false-to-true upgrade explicitly grants payload-read and reception ACK, Hooks off; decline has no registration/grant/Owner effect. Other sessions retain their Owner and service continuity. No automatic shared Stop/Start, Host replacement, transport child restart, wildcard recipient, pi/main inheritance, task replay or second authority.

## 2. Alternatives

| Choice | Result and tradeoff |
|---|---|
| Keep STOPPED generation publication and compose existing commands | Lowest change, safe for legacy profiles, but fails live join. Keep as legacy behavior; do not call it the requested feature. |
| In-place recipient policy source, stable launch descriptor, immutable live-policy history (selected) | Narrow Host admission amendment. Same Host/capabilities/Owner/heartbeat survive; no drain/authority transfer. Adds policy publication/observation and versioned configuration. |
| Replace Host under same port or start another MCP/Tunnel | Requires capability/Owner transfer, duplicates renewal or interrupts calls; second Host conflicts with requireUnowned. Rejected for this bounded design. |

The selected design avoids the earlier speculative Host-replacement transition. It needs no owner handover: only trusted configuration selection changes. A new private policy record is not a CE capability, lease, lock, workflow event or completion receipt.

## 3. Authority and trust model

The trusted Pi runtime supplies the native Session ID. The operator's native TUI confirmation authorizes exactly that Session's stable Endpoint, peer, Store/Exchange, payload exposure and reception ACK. No model tool, MCP method, message text, project path or display name may publish grants or choose another native Session. Existing advanced revoke/registration administration remains operator-only and must use the same publication path. A same-OS-user process can already edit private CE configuration; this design does not claim protection against a malicious account owner or full offline rollback by that owner. Untrusted project files, symlinks, other users and MCP callers remain outside the writer boundary.

New policy paths are canonical, owner-controlled private directories and regular 0600 files; readers/writers use existing no-follow, bounded-size, ownership/mode/ACL and credential-alias checks. No credential bytes, capabilities, payloads, model text or shell commands enter policy/adoption files. All unknown structures are validated once at the reader/writer boundary. Typed immutable values flow inward.

Only a prepared live-enabled launch descriptor may select this mode. Legacy config is never interpreted as live. A profile identity includes exact Tunnel/organization, Store directory/file, Exchange namespace/key, chatgpt Endpoint, MCP global opt-in ceiling and Hooks configuration. Any attempted change to those identity/ceiling fields through a registration commit is rejected. Registration cannot enable MCP-wide read/ACK or Hooks.

## 4. Stable launch descriptor and compatibility

Introduce a closed, explicitly versioned private binding/admission kind `ce-live-session-v1`. Existing `ce-multi-session-v1` and legacy nine-key bindings retain current parsers, immutable pairs, STOPPED requirements and deny-only behavior. Unknown kinds refuse; no fallback to legacy or another Store. The new kind must be admitted by explicit parser/contract tests, not by relaxing unknown-field validation globally.

A live launch descriptor contains the existing fixed MCP identity, Store/Exchange, lease values, exact global payload/ACK surface, baseline Hooks, and a canonical live-policy-root with a random policy identity plus genesis digest. Its path/content and the existing Node/script/client/credential identities remain included in persistent startup authorization. Normal new registration never rewrites this descriptor, Tunnel Profile, launch command or authorization record. Therefore existing run identity and startup consent remain exact while operator-confirmed Session registrations evolve beneath the explicitly selected policy root.

An initial **offline deployment/setup migration** prepares the descriptor, genesis registrations/tombstones and compatible package, with normal backed-up STOPPED gates and fresh startup permission because launch identity changes. At that single migration point the existing immutable manifest is copied into the live genesis; the previous generation is retained as historical evidence, not a concurrently writable registry. Thereafter the live chain is the only authoritative registration source for new-mode processes, while the same logical full-manifest is never independently edited in two places. Old clients fail on the new kind and must not remain writers. It is separately authorized installation work, never smuggled into a new Session's Connect on an already-running legacy runtime. Thus: live join requires a live-capable service launched once; no hot retrofit of an old MCP binary. New Connect against old service reports the version/preparation constraint and changes nothing. Old clients fail on the new kind; no compatibility claim that they enforce it. Downgrade requires coordinated Stop and removal of all new-mode processes before selecting an old, explicitly reviewed configuration.

Global MCP payloadRead/ACK must already be enabled in the live descriptor when bidirectional read/ACK is intended. Their tools/capabilities stay fixed for that Host lifetime. This is separate from each Pi Session's consent. If either ceiling is off, Connect reports that limit before publishing a purported complete messaging grant. Changing the ceiling requires offline setup, not recipient admission. Pi tool registration continues through official 1.3.0 factory/reload APIs; tool visibility never grants permission.

## 5. Policy history, revision and publication

The policy root has an immutable genesis and a contiguous sequence of immutable, digest-addressed full snapshots. Each commit envelope has a closed schema: format/policy identity, safe integer sequence, parent digest, exact fixed identity digest, random operation ID, typed operation intent and full manifest digest/content. A registration contains endpointId, trusted runtimeSessionId, epoch, active/revoked status, explicit payloadRead/ACK booleans, per-capability effective policy sequence/generation counters, presence-disclosure consent and optional existing Hooks. Limits remain bounded (at most 128 registrations including tombstones; at most 65,536 bytes per validated envelope and 64 MiB total committed chain bytes; 65,536 maximum operations). Sequence exhaustion or exceeding the chain budget is explicit operator maintenance required, preserving the last valid policy. No automatic tombstone/history GC or snapshot compaction; that requires separately authorized offline migration. Filesystem timestamps and file enumeration order are never authority or route order.

Publication uses immutable preparation plus a single exclusive-link commit, rather than a stale-breakable writer lock or a mutable current pointer:

1. Read and verify contiguous committed history from genesis, retaining exact tip sequence/digest. Capture Session/environment/cancellation and current registration. Consent is bound to this identity, target, intended grant delta and revision.
2. After confirmation, reread tip and revalidate all fences. If revision changed, no publication: return conflict for explicit Connect; do not silently retry on a newer policy. Decline creates no policy, privilege or Owner record (temporary private drafts may be removed).
3. Write the complete next envelope to an exclusively created temporary regular file, verify metadata/content, fsync it. The full next policy preserves all unrelated registrations/tombstones/epoch/Hook facts. Same native Session cannot map to another Endpoint; another Session cannot claim an existing Endpoint.
   Before step 4, durably save the exact intent locator described in step 5. The numbering there describes uncertainty handling, not an after-link persistence order. No link is attempted without a confirmed durable locator.
4. Atomically link the prepared inode to the fixed next sequence filename with no overwrite. A successful link is the publication linearization point. Another writer with the same expected parent can only get EEXIST; validate the winning commit, do not rebase the user's consent automatically. Fsync the directory before reporting durable publication. No asynchronous gap may exist between the final tip/fence check and link in that process; other writers are fenced by the exclusive next-sequence slot.
5. Link/fsync outcome uncertainty is **UNKNOWN publication**, not cancellation/rollback. Before attempting the exclusive link, persist a private, fsynced immutable intent locator: format, policy identity, native Session ID, expected parent sequence/digest, candidate sequence, random operation ID, exact typed operation/intent digest and candidate envelope digest. Use the same owner/no-follow/alias checks; fsync both file and parent directory before link. The locator is written only after explicit consent, may contain no capability/credential, and confers **no authorization or automatic replay right**. Its canonical namespace is the policy root plus a collision-resistant hash of the trusted native Session ID and operation ID; a bounded per-Session scan locates unresolved entries after crash. Before a new publication for that Session, verify and reconcile unresolved locators. If locator persistence is unconfirmed, do not attempt link. Missing/corrupt/over-budget locator history means manual reconciliation required, no fresh publish based on guesses. This locator records irreducible publication request facts, not Owner state or a second registry.
6. On the next explicit Connect, use the locator to verify that exact sequence and operation ID even when later commits exist. Same operation ID, parent, intent and candidate digest in the validated chain proves that configuration was published; a different valid commit in the exclusive slot proves a conflict. An absent slot with a matching verified parent means publication is not observed, not permission to silently retry or continue activation. Missing/forked history or unknown durability stays UNKNOWN. Read-only reconciliation returns PUBLISHED / COMPETING_COMMIT / NOT_OBSERVED / UNKNOWN with evidence; it does not repeat the link, grant, activation, Owner acquisition, transport start, message send or task. Any subsequent action requires the current explicit Connect, freshly validated state and existing policy—not authority from the locator. A valid preexisting grant can be reused, but a locator alone cannot reconstruct expired/cancelled consent. Terminal outcomes may be recorded separately as small private diagnostics; locators are retained within a fixed maintenance budget and never edited into grants.

Readers accept only a contiguous parent/digest chain with matching fixed identity and schema. Temporary/unlinked files are ignored. A visible but incompletely durable commit is a possible current configuration: authorization does not pretend fsync failure erased it. Each reader retains the highest observed sequence/digest in memory; missing suffix, regression, fork or modified known commit fails admission closed. A new process revalidates all surviving history from pinned genesis; it cannot detect a total same-user offline restore of all files and does not claim to. The filesystem model permits either durable prior or new commit after a crash; no concurrent live rollback is supported. Missing/corrupt history blocks messaging and reports reconciliation; it does not elect another Owner. No side-effecting replay.

Epoch is registration incarnation, separate from global sequence and Owner fencing. Revoke creates a retained tombstone at the current epoch; explicit reauthorization increments epoch. Permission changes for the same active native Session preserve epoch but require explicit operator publication for increases. Every payloadRead/ACK grant change records the commit sequence in that permission's independent `effectivePolicySequence` counter; unchanged permissions retain their old counter. The value is strictly monotonic whenever that bit changes, in either direction, and is bounded by global sequence. Endpoint epoch, global revision and Owner fencing do not stand in for this permission revision.
Genesis initializes each permission effectivePolicySequence to 0; a registration created in successor N initializes both counters to N, including a disabled bit. Every transition bit change must set only that permission counter to the new commit sequence; an unchanged bit must preserve it. Readers validate this delta against the parent envelope, so a writer cannot preserve or forge an old generation during reauthorization. Both counters are integral nonnegative sequence values. No runtime stores an evolving last-true history: its loaded generation is captured once at factory load, or absent when loaded disabled, and never refreshed except by official replacement.

For each permission, a runtime's captured eligible generation is `lastGenerationWhereLoadedTrue`. Its operation is admitted only if `loaded.lastGenerationWhereLoadedTrue === current.effectivePolicySequence` AND both loaded/current bits are true. Legacy v1 still uses its original loaded-current bit intersection; this is not a silent weakening of an old active session. Fresh registration with true loads that exact current generation. Unrelated B addition or changes to the other permission does not invalidate A. If a permission narrows, an old runtime fails immediately. If it later broadens, the current effective generation advances, so the old runtime remains denied. Only an official reload that captures the new true generation and proves same Session/Endpoint/epoch/mapping/policy identity can re-enable it. A failed reload leaves old denial. Example: old T1 → narrowed F2 → widened T3: old last-true T1 ≠ current T3, still denied; after verified reload last-true T3 = current T3. Metadata remains allowed. This resolves D1 security REWORK; implementation must prove true→false→true for read and ACK separately and mixed true/false cases.

Restoring old files or an old epoch/generation does not revive an already-observed revoked runtime or permission. Reauthorization is not automatic Connect recovery for a tombstoned registration. No sequence is an Owner fencing token, message receipt or business completion authority.

## 6. One Host, one Owner: admission and operation semantics

Add one narrow code-only `VerifiedRecipientPolicySource` to the existing Host construction contract for live mode. It returns a validated immutable recipient snapshot selected from the trusted root. Host identity, endpoint allowlist, own payload/ACK opt-ins, capability map, Store connection and Owner remain construction-fixed. Static mode continues using the old frozen recipients. The new source cannot supply capabilities, sender, Session/incarnation, Store, Exchange, TTL, Hooks or arbitrary operation callbacks.

The live snapshot's recipient set is exactly active Pi registrations (adapter pi, exact stable labels). Host `send` synchronously captures/validates it once while resolving the recipient and retains that snapshot through the synchronous Storage send. The surrounding bound-port admission must use that **same snapshot**, not perform a second independent policy read with contradictory authorization. Compose a prepared typed operation inside existing synchronous admission/Host execution; no await, untrusted callback or async payload load between selection and Storage authorization. The source remains in outer composition; the Host receives a typed policy port without importing Tunnel filesystem code, preserving dependency direction. The fixed chatgpt endpoint cannot send Pi→Pi or impersonate a Pi Session.

A further live-only routing precondition is required: before the **first** message to a newly registered target, trusted composition observes its existing Participant identity and Exchange membership using private read-only storage helpers. This does not join/provision, acquire Owner, inspect payload or alter Store. Existing `sendMessage` checks sender membership but not the recipient join boundary; existing `runMessageRead` rejects at/before recipient join. Therefore a pre-join target must not be offered as message-ready or admit first creation until activation/join completes. Membership is retained, so later Disconnect alone does not remove addressability. This is a narrow Host admission extension with existing SQL/schema and existing legacy send semantics untouched, not a new message router.

Linearization: the policy snapshot read is the admission point, conditional on successful snapshot validation; an operation admitted before a concurrent revoke may finish, exactly as current deny-only semantics. Operations starting after completed publication must see the new tip and deny revoked targets. The implementation must prove this fresh-read behavior under the chosen filesystem mechanism; cached file watchers cannot be the authorization source. Message create/read/ACK retain their independent Storage transaction boundary and exact current Owner/lease/fencing/capability checks. A policy commit or adoption acknowledgement is not proof of delivery.

MCP own `renew`, inbox, payload-read and ACK remain governed by fixed launch ceiling and surviving authorized policy. Revoking B removes sends **to B**; it does not remove B-originated history from shared chatgpt inbox or invalidate A. If zero active registrations survive, new messaging/renew admission follows existing fail-closed behavior; cleanup/end remains possible. Do not discard a live cleanup handle. Invalid policy is not lease extension or automatic recovery.

Terminal bound state is monotonic for that MCP incarnation: ACTIVE may transition to WRITE_BLOCKED, CLOSING or CLOSED, never back. In particular, revoking the last registration may permanently stop renewal under the existing contract. Adding B later does not restart heartbeat, reacquire/renew expired ownership, resume capabilities or clear WRITE_BLOCKED. Connect may report B configured/bound and policy observed, but must return `MCP_OPERATION_BLOCKED` (new sanitized composition diagnostic, not a frozen protocol state), cannot report messaging-ready/Reachable true, and performs no automatic shared restart or Owner recovery. A healthy transport is compatible with a blocked message port. Operator-directed reconciliation/restart, with current Owner safety checks, is a separate advanced path outside OneConnect's automatic behavior. New Endpoint live join is guaranteed only for a compatible **operational** live service; it cannot safely revive a terminally failed runtime.

Pi factories load only their trusted native Session projection at startup/reload; their existing deny-only loaded/current epoch intersection is retained and extended with the per-capability generation equality in §5. Newly created B can bind using existing requireUnowned and independent process mutex without a transport-STOPPED requirement, provided the **live-aware configuration read/activation path** verifies fixed descriptor identity and a valid current B projection. Legacy activation still uses its existing STOPPED lock. A live activation never modifies transport config. Host/Store independently rejects an existing B Owner, including an expired one; no adoption based on Session text.

A false/false-to-true/true active Pi upgrade uses official reload after publication. Old runtime closes/drains admission and transfers the exact local mutex/mapping through the existing supported reload handoff; the new runtime verifies unchanged native Session/Endpoint/epoch/Store/Exchange plus the explicit successor grant. Host resume reissues capabilities only for its same ATTACHED, currently owned active mapping under the new loaded policy, without ownership acquisition or fencing changes. If reload transfer/resume cannot prove those facts it refuses; it cannot end/take over another Owner. No MCP Host resume/transfer is needed. This path must be covered separately from fresh B activation.

## 7. Adoption observation and Connect transaction

A run-scoped private observation separates **policy observed** from **bound port operational**. It is not a grant, lock or CE receipt. After validating a snapshot, new-mode MCP records fixed launch digest, policy identity, tip sequence/digest, actual process identity, current chatgpt Owner/incarnation identifiers, exact bound-port state (ACTIVE / WRITE_BLOCKED / CLOSING / CLOSED), renewal status (RUNNING / STOPPED / UNKNOWN), terminal reason, and observation time; no bearer token. Only a local synchronous view of the existing bound endpoint plus verified current ACTIVE Owner/lease can attest operation eligibility. Merely reading a policy or probing transport must never create an operational attestation. Record states and revision are serialized together; a terminal-state event immediately supersedes an older ACTIVE record, and old asynchronous work cannot overwrite it. Policy observation can continue while WRITE_BLOCKED, but must retain terminal eligibility false. Manager independently validates actual run/child identity, current Owner/lease and a fresh record; a stale successful record is not live authorization. Stale, absent or unverifiable facts are UNKNOWN, not success. No new authority is acquired; the bound port still decides each call.

For version-one implementation, the exact child identity must be discoverable and verified through the managed tunnel-client process tree and process-start identity, together with unchanged background run identity. If the client cannot provide a reliable child identity on an intended platform, return policy-adoption UNVERIFIED on that platform and stop feature acceptance; do not treat file age/PID alone as proof. This is an explicit implementation stop condition. Observation of sequence N plus unchanged identity/epoch/permission generations for B in the current successor may satisfy the policy-observed dimension; if B changed since N, wait for the exact current revision. Messaging readiness additionally requires the same actual bound port ACTIVE, renewal RUNNING, a current ACTIVE Owner/lease, and measured transport health. WRITE_BLOCKED/CLOSING/CLOSED is never ready regardless of policy revision or transport health. Fresh checks are observations, not guaranteed future availability or operation authority. Revocation gates every actual operation regardless of the last observation.

Connect flow:

- Validate Native/runtime, live descriptor compatibility, real native Session and scope before publication. For a missing registration or false/false upgrade, one dialog previews own Endpoint, Store/Exchange/peer, payload exposure/ACK, exact Endpoint-label visibility to configured peer, and separate opt-in for advisory presence disclosure. Hooks remain off and independently authorized. For true/true active registration, reuse those grants without repeating that consent; absent presence disclosure means Active=unknown to peers until separately consented. Revoked/foreign/tombstone or unknown old release refuses.
- For a stopped transport lacking current persistent startup permission, combine the **explicitly separated** startup scope disclosure/consent into the same first dialog where possible; if a preexisting true/true Session still needs startup permission, that missing permission must still be confirmed. The implementation must not promise zero necessary security prompts or silently grant a changed script/client/credential scope. Any decline before publication leaves configuration/grants/Owner untouched. Persist startup permission only after a matching accepted scope; its durability unknown stops.
- Publish/reconcile policy only after consent and fences. Registration durability confirmed does not create a binding. Invoke official command `ctx.reload` if needed, using the existing finite same-Session/revision/environment continuation with append-history consumption. The continuation carries no grant and performs fresh checks; integrate activation consent into the original confirmed intent rather than request a second identical dialog. It cannot survive a changed target or broaden consent.
- Bind/resume only B after the verified live projection; do not alter other Pi or MCP Owners. If binding fails after publication, retain the grant and report configured/unbound. Later Connect is explicit reconciliation, not automatic retry of an unknown mutation.
- If STOPPED, start through existing Manager scope/identity/authorization checks and then wait for current health/adoption; if RUNNING, verify compatible descriptor/run and reuse it without start/stop/replacement. Concurrent Starts remain serialized by existing Manager ownership/lock. Registration publication never touches its launch Profile, so it does not invalidate that exact scope. If external/unknown run or lifecycle race occurs, report binding/policy/transport separately and stop; do not interrupt another Session.
- Report own Endpoint and lease, read/ACK grants, published/adopted revision and separately measured transport health. **CONNECTED is transport only**; do not label messages verified without real peer evidence. Timeout leaves known registration/binding state and reports adoption/transport unknown. No rollback of grants or resend is automatic.

User cancel before commit is clean cancellation. After configuration publication, activation or start has begun, cancellation closes the continuation/new admission and reports the precise committed boundary; already committed configuration is retained. It does not remove history, revoke grants or stop shared transport. Normal Disconnect stops own admission/renewal and uses existing release/detach once, retaining registration/grants and shared Tunnel; advanced Stop remains a distinct action. Unknown own release latches existing fail-closed recovery, no loop/rebind.

## 7A. Multi-client identity and discovery

### Existing capability and minimum missing interface

Registration authority remains the same full-policy manifest: trusted native Session ID → stable Endpoint + epoch + per-Endpoint grants. The current Pi identifies itself via trusted sessionManager, its factory projection and binding; `/ce-status` reports its own lease, while selected sessions reports configured active labels only. Current `ce_send.to` already routes by exact label through Host/Storage checks. Current MCP has message tools but no Endpoint target-discovery tool, and inbox discovery is not identity discovery. No automatic redirect, second registry or shared pi/main fallback is added.

Add an optional, explicitly live-enabled closed `ce_endpoints` MCP tool backed by an Endpoint-bound read-only discovery port in existing composition. Input is an empty object: no sender, target, Session, Store, Exchange, cursor or capability parameter. Keep existing send/read/ACK tool schemas and pi/main data unchanged. Existing MCP surface stays unchanged for legacy bindings. This is a private MCP/Host interface amendment with targeted contract-pin tests; it does not alter frozen Protocol entities. If a particular frozen tool surface prohibits this opt-in extension, implementation must stop for that specific additional authority. Pi exposes the same typed own-identity/target projection through its existing status UI without enumerating other Pi Sessions.

### Visibility and four separate states

Before any identity/Store observation, trusted composition filters policy to **caller self plus the exact currently send-authorized recipients**. An omitted Endpoint has no label probe, count, existence cursor or error difference. No native Session ID, Participant/Session/Owner/fencing ID, path, mutable display name, payload, another Endpoint's payloadRead/ACK/Hooks or hidden grant is disclosed. Exact Endpoint labels are shared with the configured peer by explicit first-Connect consent. `presenceDisclosure` is an independent opt-in covering **both Exchange membership/first-join observations and current Owner/lease liveness**; without it Active and the membership-dependent portion of Reachable are unknown. Policy still internally enforces membership before first send. Actual `ce_send` responses remain truthful and may themselves indirectly reveal pre/post join timing to an authorized caller; the design makes no confidentiality promise that such outcomes hide membership. Discovery adds no extra membership transition oracle, and no fabricated send success/failure is permitted. Target grants never confer caller capability. Shared `chatgpt/main` does not identify or isolate individual ChatGPT conversations.
The first-Connect sending consent explicitly discloses that an authorized peer may infer first-join/addressability changes from real send outcomes even when optional presence telemetry is withheld. This inherent consequence of enabling truthful exact-target messaging is distinct from permission to publish Owner/lease or membership status via discovery. Declining messaging consent publishes no new registration/grants/Owner. Revoking optional presence consent masks both Active and Reachable (including reasons and view digest) across membership transitions; it never fabricates Message creation or silently broadens telemetry. Existing registrations migrate with optional presence disabled until separately consented.

Result is bounded to 128 visible targets plus self, with no truncation: over-budget or invalid visible input fails with one generic refusal. Client-visible self includes caller's already-known effective operation booleans only; targets expose exact adapter/endpointId, `registered:true`, caller `authorized:{send:boolean}`, and tri-state `active`, `reachable` plus fixed reason. Responses have observation time and a digest of only this visible projection. Global policy sequence/digest and hidden-target counts stay private to composition. The digest is neither a permission, lease nor send reservation. True/false/unknown are explicit enums, not one online boolean.

1. **Registered**: active non-tombstone registration in this policy. It does not imply durable Participant, permission, Owner, transport or processing. Revoked/foreign identity is never listed.
2. **Authorized**: the invoking caller has the policy relation permitting the named operation toward this exact target, evaluated under caller's own grants. For visible targets this is the current send-recipient grant; it does not imply that Exchange-membership/Owner/health preconditions are met, that a send will succeed, or that the target is readable/executable. It never exposes or inherits the target's private grant. Filtering uses this static authorized target set, not target presence. Membership and final Storage checks remain separate.
3. **Active**: advisory observation that exact Endpoint's committed Participant has a current Owner matching an ATTACHED Session and ACTIVE lease. Absent/detached/expired is false; corruption, clock/read uncertainty or withheld presence is unknown. It cannot create/repair/take over/renew an Owner or reveal Session IDs. Independent public ownership/lease reads do not promise a coherent snapshot, so a new **private deferred single-transaction, one-clock aggregate** uses existing validated row parsers/SELECTs for only filtered authorized recipients. No new SQL/schema, new capability scope, raw Store handle or SQL reaches MCP. Failure is generic and tri-state; Host/Storage remains the final message authority.
4. **Reachable**: this exact target is admitted for durable addressing by the live MCP at the adopted policy and its invocation transport is serving. It also requires existing Participant/Exchange membership from the trusted private observation, because sending before the immutable join boundary would make the message unreadable later. Active is separate: an already-joined recipient with released Owner may still be reachable for durable storage under unchanged Storage semantics, but is not processing. Pi Reachable requires Manager health/adoption, otherwise unknown. A current successor changing that target's epoch/grants after the observed adoption makes reachable unknown; revoked target is omitted. This says nothing about cloud delivery, recipient processing, ACK or task completion.
   A terminal WRITE_BLOCKED/CLOSING/CLOSED message port makes Reachable false for its write targets even if the policy was observed and transport healthy; missing fresh operational evidence yields unknown. This does not expose another Session's private grant.

Discovery and send use the same policy/visibility algorithm but fresh snapshots per operation. A list is advisory and may be stale immediately; a revoked target cannot be sent merely because it was listed. Discovery performs no probe, join, Inbox read, message send, wake, Owner change or Hook. Actual send rechecks recipient, membership, caller authority and Storage transaction; it never falls back, redirects or retries after uncertainty.

### Target selection without pi/main

**Client intent is a boundary, not a server authorization proof.** For a reply to an already-authorized incoming message, the caller may reuse its exact `from` as correlation only if the caller still explicitly intends to reply to that Session. Otherwise, if multiple targets are visible, the client should require the user to explicitly select a target, show those exact labels or ask a plain-language selection question. The MCP cannot guarantee ChatGPT UI or model behavior, and a bare `ce_send.to` label proves only exact addressing permission, not that the user selected that label. Therefore this is a client-side behavioral acceptance requirement, not an assertion that the MCP enforces confirmation. There is no per-message signed selection token in this design. If user-intent proof is a required security boundary rather than a usability requirement, a separate trusted selection token bound to Exchange, exact target and intended message must be designed and authorized first. Current-user intent cannot be inferred from latest registration/Owner/connection, a shared ChatGPT identity, model switch or Tunnel ordering. No reliable selection/correlation means the client should ask, not pi/main or most-recent routing. Human labels are never security identity and messages are never auto-migrated.

### Multi-client consistency and acceptance

With A connected, B joining after consent/adoption adds only B's visible target; exact ChatGPT sends can address A and B independently. A message cannot be read/ACKed by B. B Disconnect retains registration/grants/membership, sets Active false, leaves A Owner/transport intact; B's persisted reachability follows those facts rather than an online flag. B reconnect reuses its stable Endpoint and remembered grants without duplicate registration or repeating consent. Duplicate labels or foreign runtime ownership are refused; expired Owner is not automatically repaired/taken over. In-flight list/send/revoke has explicit per-operation snapshots and admitted-before-revoke completion; current tip wins later admission. ## 8. Concurrency, crash and rollback matrix

| Boundary/failure | Required outcome |
|---|---|
| B and C confirm same parent | One sequence slot wins; loser conflicts, no automatic consent rebase; A unchanged. |
| B publication overlaps revoke A | Exclusive next slot serializes full snapshots; no lost revocation. A operations admitted before the selected snapshot may finish; subsequent fresh snapshots deny. |
| Revoke B then reauthorize B | Higher epoch; old B factory cannot revive; explicit consent and fresh projection required. |
| Writer dies before exclusive link | No policy change, no Owner acquired. Prepared files are non-authoritative. |
| Link succeeds; directory fsync/result lost | UNKNOWN publication; explicit operation-ID reconciliation. Do not call it CANCELLED or resend messages. |
| MCP sees new policy before writer reports success | New admission may occur under visible valid configuration; writer reports uncertainty honestly. No premature denial of a real commit. |
| Child crashes during observation | Same as existing crash: Owner persists and may expire; no new process takes over. Stale observation invalid; recovery remains operator controlled. |
| Policy corruption/missing suffix/fork | Deny affected new admission, retain cleanup handles, no automatic previous-version fallback; report integrity BLOCKED. |
| Pi reload fails after grants commit | Grant persists, unbound or old denied runtime; explicit next Connect rechecks, no duplicate registration or takeover. |
| Stop races live publish | Policy commit is independent of launch lifecycle; Connect may remain configured but not connected. No assertion of running adoption from a dead child. Next explicit Start uses same descriptor and validates newest complete history. |
| Timeout awaiting adoption | Configured/bound can be true while adoption unknown; no full messaging-ready claim and no automatic shared restart. |
| Need to undo a registration/grant | New successor narrowing/revoke commit, retaining tombstones. Never move a pointer backward or delete commits. |
| Need to revert binary/architecture | Planned operator Stop, verify no dependent new-mode hosts, restore reviewed legacy setup with fresh scope consent as required. Outside Connect and outside this design-only execution. |

No failure path changes DELIVERY_UNKNOWN to CANCELLED, replays business effects, manufactures ACK/completion or treats policy sequence as Owner fencing. Old binaries cannot be proven revoked by new configuration; deployment must identify and stop legacy writers before live activation.

## 9. Hooks and Pi 1.3.0 compatibility

New registrations have no Hooks. A consent-only read/ACK or discovery upgrade preserves any previously and separately authorized existing Hook facts byte-for-byte; it adds/enables no rule, clears none and changes no Hook authority. Existing configured rules retain metadata-only event, static-command admission, deadline/output bounds, durable at-most-once execution markers and close/drain behavior. MCP Hook runner retains launch rules and only narrows them against current matching recipient/epoch/rule facts; dynamic joins add no MCP Hook rules. Pi reload can load separately authorized existing rules for its own registration. Enabling/changing MCP Hooks requires separate explicit offline configuration, not registration publication. No live-admission record or observation fires a business Hook. Already admitted Hook work follows existing semantics; revocation does not erase execution history.

Pi uses only trusted sessionManager ID, appendEntry/getBranch/getEntries, command ctx.reload and documented session_start/reload/shutdown APIs. No forged IDs, direct runtime mutation or tool-registration bypass. Dynamic visibility is handled by normal factory registration after official reload. Context changes, cancellation, stale continuation and branch replay are fenced as before. Official Pi API use is based on the installed 1.3.0 documentation/source already investigated; implementation must recheck exact types/examples before editing, and report any incompatibility rather than inventing an API.
