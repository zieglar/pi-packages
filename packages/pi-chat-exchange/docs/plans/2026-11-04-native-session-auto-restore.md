# Native Session automatic CE restoration — draft after user direction

## User direction and actual defect

The user explicitly asked why a separate recover command is necessary and requested direct automatic restoration. This supersedes the earlier extension design requiring explicit /ce-tunnel recover and branch-visible original metadata. Existing authorization still preserves the original native Session/Endpoint, permits necessary expired-Owner/offline mutex maintenance, and forbids live takeover, history rewriting, frozen Core/Protocol/Storage changes, publishing or unrelated configuration changes. No repeat permission is needed for that same repair. If implementation actually requires changing frozen authority or automatic live/stale takeover, stop and surface that separate expansion.

Actual read-only evidence: one ce-mapping, one ce-lifecycle-blocked in the original persistent native Session. Current conversational branch has neither; even the failure's own ancestor branch lacks the mapping. Pi context branching/compaction separated the records. Original process is still alive and offline maintenance has not run. r3's fake-array harness failed to represent the real SessionManager tree and its branch-visible precondition is not applicable to this Session. The old maintenance packet is SUSPENDED.

## Product behavior

- Remove the separate /ce-tunnel recover command and duplicate confirmation step. Initial connection/registration and ordinary explicit disconnect controls remain as existing product operations.
- A previously bound, currently registered native Session should automatically restore its own CE binding on startup/resume/reload when existing authority primitives permit it. Conversation tree navigation/compaction must not select an old CE binding or make the latest native Session binding disappear.
- Restoration must use the same native Session and currently selected Endpoint; no new registration, sender selection or endpoint argument. Current policy, ordinary process mutex and Host checks remain mandatory. Attached is reported only after real ACTIVE+exact mapping verification.
- An active Owner belonging to another binding, any uncleared expired Owner, live old process/mutex, process failure cache, uncertain/incomplete attempt or invalid history remains a concrete refusal. No automatic stale-ownership recovery tool or mutex reconciliation at startup. The already authorized one-time offline maintenance is still needed; once completed, starting the same Session should restore without a recover command.
- Explicitly deactivated messaging remains deactivated. Do not interpret any arbitrary released old binding as permission to undo user intent.

## Recommended model: native Session CE lifecycle projection

CE ownership and binding identity belong to native Pi Session, not to a conversational branch. Read the full append-ordered SessionManager.getEntries() as the lifecycle record source, and verify that source against the actual persistent native Session file before an automatic restoration which creates/adopts authority. The conversation branch remains relevant for context mutation fences during in-flight work, but does not choose a prior CE mapping or erase a committed native lifecycle event.

Projection yields one latest valid native binding and unresolved diagnostic set. Historical records are identifiers and failure evidence, never capabilities. Only ordinary policy/mutex/Host resume or requireUnowned begin can establish authority. Pure metadata projection must never clear a process/global failed cache or open business admission by itself.

Three alternatives considered:
1. Keep independent command and permit historical baseline only after confirmation: superseded by user direction and leaves routine restart UX broken.
2. Simply use the last mapping from full history and ignore failure records: rejected, could launder unknown writes and explicit release intent.
3. Recommended: one append-ordered native CE lifecycle projection, strict commit/failure/release replay and ordinary authority validation. Reuse existing event formats where possible; add only irreducible provenance/intent needed for safe restoration.

## Proposed checks and journal rules (review before implementation)

1. Boundary input: validate complete history, unique stable IDs, custom event schema and exact native-file header/session identity once. Bind Store/native Session/current active registration/Endpoint and full selected policy/environment. Missing real persistence/full history, malformed CE evidence or foreign Endpoint failure denies. Do not log message/payload bytes read for consistency checks.
2. A current branch mapping may not override a later native lifecycle event. Fold mappings/releases/failures/recovery records in full append order. Identical normal resume mappings are allowed. A different durable mapping must have an exact prior release of the predecessor or a complete verified restoration attempt/mapping/commit. Reject conflicting, malformed, orphan or partial transitions. Preserve current complete mapping-chain and later-failure denial tests, adapting only the old assumption that hiding records in a conversation branch erases native state.
3. Old v1 recovery formats remain readable with exact shape/ref/order checks. Full native history now defines visibility; conversation rollback cannot revive a pre-commit mapping. An incomplete attempt anywhere in native history still denies. A complete commit supports only ordinary current policy/mutex/Host revalidation. Unknown future journal versions deny.
4. For the actual initial historical case, require a unique original binding tuple in pre-attempt history, deterministic source entry ID (earliest equivalent entry), all matching unresolved native/Endpoint failure IDs and no prior incomplete journal. All source IDs precede attempt; all applicable earlier failures are enumerated exactly, not merely a subset. Existing failures on other Endpoints deny. If more than one unexplained historical tuple exists, stop instead of selecting latest arbitrarily.
5. Automatic repair may create a fresh durable Session ONLY through ordinary beginSession(endpoint,{requireUnowned:true}) after ordinary mutex admission and current policy. It must retain original Participant/Exchange/Endpoint and produce a distinct durable Session, then verify exact ACTIVE Host status. It never invokes takeover/reconcile or resumes a historical tuple as if it were credentials.
6. Before mutex admission or any restoration journal, read-only verify that the current Endpoint resolves to the original existing Participant, current policy resolves to the original existing Exchange, and the original membership exists. Missing/mismatched identity is a refusal, never UNOWNED. Read ownership for that verified Participant; known active/expired Owner refuses before any attempt. Repeat identity/ownership checks immediately before Host writes; the final ordinary requireUnowned begin remains the race boundary. Obtain the ordinary runtime/process mutex before appending attempt: local exclusion is not Host authority. A held/uncleaned mutex must refuse before a restoration journal, so an operator can finish required cleanup without startup creating an incomplete business attempt. Append+verify attempt BEFORE Host authority writes. Use an exact new automatic journal version capturing policy, Store/native identity, earliest equivalent source mapping entry ID and ALL matching unresolved failure IDs. Do not fabricate branch ancestors. Uncertain mutex/journal results retain fail-closed handling; never fabricate Host end/release proof to retire a local handle.
7. Verify the complete persistent Session history equals the captured manager history (except native header) before restoration and immediately before Host writes, using the same held O_NOFOLLOW regular-file fd, stable path/inode/UID and bounded supported file policy. Thereafter accept only the exact expected appends; verify+fsync attempt, mapping and resolution before publishing generation. Same-inode unexpected append, truncation, replacement, malformed/partial lines or missing complete history denies. This snapshot/journal is not a lock; normal scope mutex prevents concurrent CE admission. Preserve fail-closed cleanup if later validation notices external interference. No same-UID malicious writer/power-loss guarantee is claimed.
8. Current process/global runtime failures require restart, unchanged. Automatic eligibility is closed: (a) a stable mapping with no unresolved failure may only use normal resume against the same ACTIVE tuple; (b) the FIRST historical repair requires no prior recovery journal, one unique old tuple, at least one matching failure, no release/deactivation, and all preflight checks; (c) a complete recovery commit without later failure only permits ordinary current revalidation, never another recovery begin; (d) a validated future normal-shutdown release without unresolved failure may use ordinary begin preserving identity; (e) explicit deactivation, legacy unknown release, any later failure after a commit, any incomplete attempt or invalid history remains Detached/refused, with no new restoration attempt. UNOWNED alone never clears uncertain results. Writer visible-then-throw or fsync failure still latches/drops and never reports success.
9. Reuse existing shutdown/activation coordination. Validate context/native file/full history/policy/environment before mutation; no await gap between final fence, ordinary admission and Host synchronous writes. Session replacement aborts/drains as before. No transport operation is implicit in CE binding restoration.
10. Future ce-messaging-released records add exactly intent: "shutdown" | "deactivate". shutdownCe("messaging-deactivation") writes deactivate; verified normal quit/session replacement writes shutdown; reload remains transfer with no release. Startup must preserve Detached for deactivate and legacy five-field release, requiring existing explicit Activate/Connect; a later verified explicit activation starts a new binding chain. Full-history replay accepts exactly legacy five fields or the new six fields. Initial onboarding/new registration stays unchanged.
11. Remove the recover shortcut/completion and associated product instructions. Report the actual failed prerequisite (active/stale Owner, old live mutex process, invalid/partial native journal, explicit deactivated state) without leaking payloads/capabilities. Do not add another user-facing recovery command or repeated approval dialog to replace it.
