## Reply correlation fix

A received reply may be the immediate parent of a new reply. Previously the Store required that parent to point to itself as a root request. A valid request → reply → confirmation therefore failed with `MESSAGE_READ_REJECTED` on the confirmation despite a successful authorized read.

The fix removes only that root-only restriction. The immediate parent must still exist in the same Exchange, reverse the exact sender/recipient pair, postdate the caller's membership boundary, and identify the caller's current target Owner Session and fencing token. It does not grant the sender read permission over its own outbound Message or permit a different Endpoint to join the chain. Idempotent replay keeps the original Message identity. `replyTo` remains the immediate parent; no transcript, payload or ownership inference is added.

This reproduces the failure pattern reported for the associated confirmations to audits #804, #805, #807, #809 and #811. It is a source/isolated-Store reproduction, not a claim that those production exchanges were replayed or modified.

The extension also makes inbound-only read guidance explicit and warns against reading the sending Endpoint's outbound ID. `CREATED` still proves persistence only; ACK is reception evidence, and CE supplies no Wayforge business-completion authority.
