## Installation routes

`@zieglar/pi-chat-exchange@0.2.0` is published on npm. Using a registry you trust, the native managed npm route is:

```sh
"$CE_APPROVED_NODE" "$CE_PI_CLI" install npm:@zieglar/pi-chat-exchange@0.2.0
"$CE_APPROVED_NODE" "$CE_PI_CLI" list
```

Use approved absolute Node and Pi 1.3.0 CLI paths, and npm supplied by that Node with private config/cache and ignore-scripts. Pi suppresses peer auto-installation; its independent Host supplies Pi peers. The install-command evidence for 0.2.0 was produced against an owned loopback registry, not public npm; that historical test does not itself certify public-registry installation. Always confirm the exact version actually resolves before relying on it.

[Independent installation](../independent-install.md) describes the separate prebuilt tarball asset fallback and the mandatory safe uninstall/upgrade/rollback procedure. GitHub assets are downloaded/hashed before physical prefix installation, not passed as Pi URLs; monorepo source loading is a development route, not managed npm. Do not load two copies.

## Producer record and artifact integrity

Author uses frozen pnpm 12.9.1 dependencies with ignore-scripts and approved Node. Run `pnpm run package:pi-extension` in the package: build → validate disk closure → validate native pack inventory → pack without hooks. Retain the exact `.tgz`, SHA256/SRI, inventory, fixed commit, lockfile hash, tool versions, argv/private environment and test evidence. Never rebuild on consumer machines or substitute an old archive for the tested artifact.

Where 0.2.0 is distributed as a GitHub Release asset, it is the exact tested `zieglar-pi-chat-exchange-0.2.0.tgz` plus `SHA256SUMS` generated with `shasum -a 256 zieglar-pi-chat-exchange-0.2.0.tgz > SHA256SUMS`. Consumers download both assets and run `shasum -a 256 -c SHA256SUMS` before installation. The archive is never rebuilt between validation and upload.

**Integrity claim limits.** The harness computes the artifact's SRI/SHA256 metadata, serves exactly those bytes over the owned loopback registry, and compares every installed payload file byte-for-byte against the tested archive. That is metadata plus installed-payload byte identity. There is no corrupted-metadata/corrupted-payload **integrity-rejection negative**, so no claim is made that a consumer npm would refuse a tampered artifact.

The third-party LICENSE evidence gates are closed: the per-version evidence is retained in the author's private evidence store and summarized in `docs/license-audit.md`, which is repo-only and not distributed in this tarball. Whenever the shipped pins change, the retained evidence must be re-confirmed against them. Cloud transport validation is a separate, still-undecided scope and no cloud claim is made by 0.2.0.
